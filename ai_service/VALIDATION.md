## Исправление длинных видео

В исходном кейсе указаны ролики 10–145 с и предел ожидания результата 5 минут. Ограничения входа 60 с нет. Свежий локальный FFmpeg-просмотр метаданных подтвердил 7 файлов длиннее минуты: X-4/X-47 — 72,70 с, X-5/X-48 — 71,60 с, X-13 — 65,30 с, X-14 — 142,53 с, X-39 — 78,73 с. Все 42 файла меньше текущих ограничений 180 с/64 MiB.

Причина прежних сбоев X-4/X-5/X-47/X-48 — общий предел в три объединённых кандидата. Такая же ошибка встречалась на коротких X-1/X-45; X-46 завершился timeout. Это не подтверждало жёсткий предел длительности в 60 с.

Изменения текущей версии:

- Кадры декодируются по окнам; перекрытие используется повторно. Все исходные JPEG больше не удерживаются сразу.
- Причинные кадры кандидатов сохраняются как исходные PTS и повторно извлекаются с проверкой PTS для уточнения.
- Шаг 4 с сохранён. Окна до 60 с — 6 кадров/перекрытие 1; после 60 с — 12/2 (`long_video_threshold_sec`, `long_video_frames_per_window`, `long_video_overlap_frames`).
- `max_refinements: null` требует проверки всех объединённых кандидатов до общего дедлайна. Явный целый предел остаётся доступен и при превышении вызывает `failed`.
- Timeout, исчерпание RAM/VRAM и незавершённая проверка не возвращают вердикт `no_violation`.
- Лимиты сохранены: multipart 64 MiB, вход 180 с, pipeline 270 с, API 300 с. Это ограничители, а не обещанная скорость.
- При новом запуске Ollama автоматически выбирается prompt cache 128 MiB для ограниченных характеристик/доступной RAM менее 4 GiB; иначе допустим 512 MiB. Это не лимит всей памяти модели. Старый процесс Ollama необходимо перезапустить для применения нового значения.

## Что остаётся нерешённым

Качество бинарных ответов низкое, есть ложные события, пропуски и операционные сбои. После изменения длинных окон полная validation/test-оценка не повторялась; X-14 показывает ложные события и очень низкий остаток RAM. Обработка всех длинных роликов на произвольном оборудовании не гарантирована. Шесть узких правил включены, пять гипотез отключены; полного нормативного покрытия разметки нет. Публичный доступ не опубликован, физическая автономность без сети не проверялась. Система не заменяет проверку человеком. Дедлайн не гарантирует мгновенную остановку вычислений Ollama.

Следующая идея — YOLO11n + OpenCV: [официальная таблица](https://docs.ultralytics.com/models/yolo11/) указывает 2,6 млн параметров YOLO11n. В проекте такой pipeline не установлен и не измерен; для купюр/ключей нужна предметная разметка. Дообучение никаких весов здесь не проводилось. Это предложение следующего pilot, не готовое исправление результатов текущей модели.

Команды запуска, повторного benchmark и `Audit-Results.py` приведены в README. Повторные прогоны сохраняйте в новые каталоги, не затирая зафиксированные артефакты.


Повтор некорректного ответа модели: один дополнительный локальный вызов с теми же кадрами, правилами и абсолютными PTS. Повтор не получает метки или правильного ответа, не исправляет JSON подстановкой и остаётся внутри общего дедлайна. Если повтор тоже некорректен, API возвращает failed/model_invalid_output без вердикта. Ошибки памяти и timeout автоматически не повторяются.


Дополнительная проверка X-13 (65,30 с): первоначально failed за 97,141 с из-за неверных индексов доказательств; результат сохранён. После добавления одного ограниченного повтора — done за 114,188 с, 4 кандидата проверены, 7 вызовов модели с одной повторной проверкой формата. Все 4 JPEG/PTS совпали. Итог трёх development-проверок: 3 done, 24/24 кадра совпали; ложные вердикты X-14/X-39 сохраняются. Сводка и новая фиксация: results/long_video/summary.json, results/long_video/freeze.json. Предыдущие результаты и неуспешная попытка не удалялись.
